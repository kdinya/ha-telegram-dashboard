# Інструкція для AI-агента: Home Assistant Telegram Dashboard

## 1. Правила роботи та робочий процес

1. **Обмеження на саморедагування**:
   - AI не має права самостійно редагувати цей файл (`AGENTS.ua.md` / `AGENTS.md`).
   - Якщо AI бачить пропущені правила чи потрібні зміни — він спершу пропонує їх користувачеві на затвердження.

2. **Взаємодія з користувачем**:
   - Спілкуватися українською.
   - Відповіді стислі, зрозумілі, по суті, без «води».
   - Пряма команда «виправ / зроби» — виконувати одразу.
   - Запит «проаналізуй / оціни» — спершу стиский план чи аналіз, і тільки після схвалення змінювати код.

3. **Версії та релізи**:
   - За замовчуванням оновлювати поточну версію на місці; нову версію створювати лише за прямою командою.
   - Семантичне версіонування (`v1.0.x`); нова версія = +1 патч (`1.0.0` -> `1.0.1`).
   - Для великих архітектурних змін — мінорна версія (`1.1.0`), про що AI пропонує сам.
   - При створенні нової версії синхронізувати рядки версії в:
     - `telegram_dashboard/config.yaml` (`version`)
     - `telegram_dashboard/src/__init__.py` (`__version__`)
     - `telegram_dashboard/CHANGELOG.md`
     - `CHANGELOG.md` (корінь)
     - `README.md` (якщо версія згадується в шапці/бейджах)

4. **Джерело істини та дисципліна Git**:
   - Перед змінами завжди підтягувати актуальний `origin/main`.
   - Мінімальні дифи: чіпати лише рядки, що стосуються задачі.
   - Не перетирати конфігурації користувача і не вносити breaking-зміни без попередження.
   - Коміти — стислі, у стилі conventional commits (`fix:`, `feat:`, `docs:`, `perf:`, `test:`, `chore:`).
   - Автор комітів: `kdinya <k.dinya@gmail.com>`.

## 2. Архітектура та суворі інваріанти

1. **Конфігурація адона та Ingress**:
   - `telegram_dashboard/config.yaml` — маніфест для Home Assistant Supervisor.
   - `ingress: true` з внутрішнім портом `8099` має підтримуватися завжди.
   - Токен Supervisor API (`SUPERVISOR_TOKEN`) передається змінною середовища для зв'язку з HA Core (`http://supervisor/core/api`).

2. **Інваріант RBAC (контроль доступу)**:
   - Кожен вхідний Telegram-update (команда чи callback) має проходити через `AccessController`.
   - Ніколи не показувати адміністративні чи небезпечні дії (перезавантаження/вимкнення ПК, головний клапан, перемикання кондиціонера) неавторизованим користувачам або користувачам без потрібної ролі (`admin`, `member`, `guest`).
   - Незареєстровані користувачі — відмова або обмежений guest-вигляд згідно з конфігурацією.

3. **Рендеринг повідомлень і типографіка**:
   - Рендеринг — стандартний Telegram HTML (`<b>`, `<code>`, `<i>`, `<blockquote>`, `<pre>`).
   - Ієрархія та читабельність — деревоподібні лінії (`├`, `└`) та візуальні прогрес-бари (`[▰▰▰▰▱▱]`).
   - Усі динамічні повідомлення у відповідь на inline-кнопки — через `edit_message` з підтвердженням callback (`answerCallbackQuery`), щоб не спамити і не залишати «годинники».

4. **Збереження даних і безпека**:
   - Динамічні налаштування користувачів і схеми меню — у `/data/config.json`.
   - Поза HA (тестовий режим) — fallback на локальний `config.json` без падіння.
   - Валідація JSON при завантаженні та атомарні бекапи перед збереженням.

5. **Інваріант тестів**:
   - Уся бізнес-логіка (RBAC, рендерер, конфіг-менеджер, HA-конектор) має 100% прохідні тести в `tests/`.
   - Запускати `pytest` перед кожним релізом і комітом.
